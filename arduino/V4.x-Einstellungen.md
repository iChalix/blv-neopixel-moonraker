# Arduino-Seite: NeoPixelBLVmgn V4.0/V4.1 mit Klipper

Diese Variante ist der Standard der Middleware:

```ini
[printer]
sketch_version = 4.1
```

Der Sketch selbst bleibt unveraendert; angepasst wird nur `Config.h`.

Sketch holen:

```bash
wget https://github.com/mule1972/NeoPixelBLVmgn/archive/refs/tags/V4.1.tar.gz
```

Anders als V3.0 besteht V4.1 aus mehreren Dateien (`NeoPixel_BLV.ino`,
`Config.h`, `Structures.h`, `StreamingHandler.*`, `Debugging.h`, `src/json/`) -
den ganzen Ordner entpacken und die `.ino` daraus oeffnen.

Benoetigte Bibliotheken (Arduino IDE -> Bibliotheksverwalter):

* **Adafruit NeoPixel** >= 1.2.3
* **AltSoftSerial** - wird in `NeoPixel_BLV.ino` bedingungslos eingebunden,
  auch wenn man kein Debugging nutzt

## Config.h fuer 3 Ringe mit je 16 LEDs

Die Werkseinstellung von V4.1 belegt die Pins wie der BLV-Schaltplan:

| Eintrag | Pin | `DisplayPrinterObject` (Werk) |
|---------|-----|-------------------------------|
| Neopixel 1 | 7 | `{ 1, 0, 99, -1 }` |
| Neopixel 2 | 6 | `{ 0, -1 }` |
| Neopixel 3 | 8 | `{ 1, -1 }` |

Neopixel 1 zeigt im Werkszustand also abwechselnd Hotend, Bett und Status.
Wer den Ring nur als Statusring moechte (so wie es V3.0 standardmaessig
macht), setzt:

```c
DisplayPrinterObject : { 99, -1 },
```

Mischt man Heater und `99` in einer Liste, muss
`DisplayPrinterObjectChangeByFrequency : true` gesetzt sein - die
Prioritaetslogik fuer `false` funktioniert nur mit Heatern.

Weitere Empfehlungen:

```c
// HeaterConfig[0] (Bett): 0-112 C auf 16 LEDs, Werkseinstellung 6 = bis 96 C
Scale : 7,
// HeaterConfig[1] (Hotend): Werkseinstellung 16 = bis 256 C,
// fuer ein 300-C-Hotend 19 nehmen
Scale : 19,

// Werkseinstellung 8 ist sehr dunkel
Brightness : 40,
```

## Verdrahtung Raspberry Pi <-> Arduino

V4.x fragt den Zustand selbst ab (`M409 F"d99f"`, alle 1 s im Betrieb, alle
5 s im Leerlauf). Die Middleware beantwortet jede Abfrage **und** sendet
zusaetzlich ihren Heartbeat - beide Verdrahtungen funktionieren also.

**Variante A - USB (empfohlen):** Arduino Uno/Nano per USB an den Pi. Beide
Richtungen sind vorhanden, die Abfragen werden beantwortet. Im Log steht
dann `Arduino fragt den Zustand ab (M409 F"d99f")`.

**Variante B - GPIO-UART:** Pi TX (GPIO14, Pin 8) -> Arduino RX und GND
genuegen, dann liefert nur der Heartbeat die Daten. Soll der Arduino auch
fragen koennen, braucht die Rueckrichtung Arduino TX (5 V) -> Pi RX
(GPIO15, Pin 10, **3,3 V**) einen Spannungsteiler - sonst wird der
Pi-Eingang beschaedigt.

Zwei Eigenheiten von V4.x, die in der Praxis auffallen:

* Die Abfrage geht mit `Serial.println(...)` hart ueber `Serial` hinaus,
  nicht ueber das sonst benutzte `SerialObject`. Auf einem Arduino Mega
  (dort ist `SerialObject` = `Serial2`) kommt die Abfrage also am USB-Port
  heraus, waehrend die Antwort auf `Serial2` erwartet wird. Mit dem
  Heartbeat laeuft es trotzdem - Abfragen werden dann einfach nicht
  gesehen.
* Mit aktivem Debugging belegt AltSoftSerial die Pins 8 und 9. `Config.h`
  verschiebt Neopixel 3 deshalb per `#if` auf Pin 11 - das Kabel muss dann
  mit umgesteckt werden.

Die 5-V-Versorgung der Ringe gehoert an ein eigenes Netzteil mit gemeinsamer
Masse; 48 LEDs ziehen bei voller Helligkeit ueber 2 A.

## Was V4.x anders macht als V3.0

| | V3.0 | V4.x |
|---|------|------|
| Protokoll | flaches M408-JSON | Objektmodell der RRF 3 |
| Status | Buchstabe (`"P"`) | Wort (`"processing"`) |
| Heater | Zahlenlisten | Objekte mit `current`/`active`/`standby`/`state` |
| Fortschritt | `fraction_printed` direkt | aus `timesLeft`/`job` errechnet |
| Abfrage | keine | `M409 F"d99f"` |
| Ring bei 100 % | komplett fuellbar | letzte LED bleibt auf Druckfarbe |

Die Anzeigelogik auf den Ringen (Farben, Balken, Reihenfolge der LEDs) ist
in beiden Versionen gleich. Details zu beiden Protokollen:
[../docs/protokoll.md](../docs/protokoll.md).
